# 해커톤 실행 계획

## 목표

2026년 8월 11일까지 문제의 실제성, AI의 필요성, 구현 가능성이 하나의 3분 데모와 발표 자료에서 연결되도록 합니다.

## 마일스톤

| 기간 | 결과물 | 통과 조건 |
|---|---|---|
| 7/24–7/27 | 고객·문제 검증 | 최근 행동 인터뷰 5건, 유지·수정·폐기 결정 |
| 7/27–7/29 | 데이터·MVP 잠금 | P0 흐름, 데모 입력, 데이터 원천 확정 |
| 7/30–8/02 | 클릭형 흐름 | 모바일 기준 전체 사용자 흐름 검토 |
| 8/03–8/06 | 기능 통합 | 입력→비교→재정렬→확정 동작 |
| 8/07–8/08 | 사용자 테스트 | 5명 과제 테스트와 치명 문제 수정 |
| 8/09 | 발표·데모 초안 | 문제·고객·근거·AI·결과가 한 이야기로 연결 |
| 8/10 | 기능 동결 | 백업 데이터와 녹화본 포함 최종 리허설 |
| 8/11 | 제출 | 데모, PPT, 제출 파일 확인 |

## 역할 보드

| 트랙 | 책임 결과 | 담당 |
|---|---|---|
| 방향·의사결정 | 문제·고객·범위 최종 승인 | 제품 책임자 |
| 기획·검증 | 인터뷰, 근거 로그, PRD | 기획자 |
| 프론트엔드 | 모바일 사용자 흐름과 상태 처리 | 프론트엔드 |
| AI·백엔드 | 조건 구조화, 후보 평가, 데이터 연결 | 개발 담당 |
| 디자인 | 현대적 레이아웃과 집현전 표현 | 디자이너 |
| 발표 | 3분 스토리와 질의응답 | 발표 담당 |

## 데모 시나리오

1. 금요일 저녁 6명 모임을 입력합니다.
2. 1인 2만 원, 차량 없음, 한 명 21시 귀가 조건을 보여줍니다.
3. 시스템이 충돌과 필수 조건을 설명합니다.
4. 서로 다른 장단점의 대안 3개를 비교합니다.
5. 사용자가 이동 피로 가중치를 높입니다.
6. 순위와 근거가 바뀌는 것을 보여줍니다.
7. 최종 일정 카드를 확정합니다.

## 발표 구조

1. 구체 고객의 실제 상황
2. 기존 방식에서 생기는 반복 문제
3. 인터뷰·관찰 근거
4. AI가 필요한 이유
5. 3분 데모
6. 구현 범위와 데이터 신뢰성
7. 다음 검증 계획

## 상위 위험과 대응

| 위험 | 조기 신호 | 대응 |
|---|---|---|
| 고객 문제가 약함 | 인터뷰에서 최근 사례가 나오지 않음 | 7/27 이전 고객 또는 상황 교체 |
| 범위 확장 | P0 밖 기능이 계속 추가됨 | 제외 범위와 결정 로그로 차단 |
| 데이터 부정확 | 장소·교통 값 검증 실패 | 검증된 소규모 데이터셋으로 제한 |
| LLM 출력 불안정 | 형식 오류와 환각 반복 | 구조화 출력, 규칙 검증, 폴백 |
| 데모 장애 | 네트워크·API 지연 | 캐시, 사전 데이터, 녹화본 준비 |
| 발표와 제품 불일치 | 슬라이드 기능이 실제 동작하지 않음 | 기능 동결 후 실제 화면만 사용 |

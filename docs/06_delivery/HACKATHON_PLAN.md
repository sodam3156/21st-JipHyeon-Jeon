# 해커톤 실행 계획

## 목표

2026년 8월 11일까지 인사이트에서 출발한 메인 아이디어 하나를 선택하고, 문제의 실제성·AI의 필요성·세종 적합성·구현 가능성이 3분 발표 안의 90초 핵심 데모와 발표 자료에서 연결되도록 합니다.

## 아이디어 선택 리허설

각 후보는 3분 발표 안의 90초 핵심 데모로 아래 구조를 먼저 통과해야 합니다.

1. 구체 고객과 촉발 시각
2. 현재 실패 행동과 측정 가능한 손실
3. 입력 또는 사건
4. AI가 바꾸는 판단
5. 이전과 다른 상태
6. 다음 사람이 쓰는 결과물
7. 근거·데이터 시점·사람 승인

## 선택 후 데모 설계 원칙

- 대표 사건 하나만 end-to-end로 처리합니다.
- 세종 요소를 제거하면 판단이나 결과가 달라져야 합니다.
- LIVE, VERIFIED DATA, MOCK, ROADMAP을 구분합니다.
- API·네트워크 장애에도 핵심 상태 변화를 보여줄 축소 모드를 둡니다.
- 제품에 없는 기능과 검증하지 않은 숫자를 발표하지 않습니다.

## 상위 위험과 대응

| 위험 | 조기 신호 | 대응 |
|---|---|---|
| 인사이트 없이 아이디어 고착 | IDEA 이름이 근거보다 먼저 반복됨 | D-006과 Gate 2–5로 차단 |
| 고객 문제가 약함 | 최근 행동·손실 사례가 나오지 않음 | 7/27 이전 기회 영역 교체 |
| 자료 용도 혼합 | 기술 문서로 시장성을 주장함 | source-catalog와 E-006 경계 적용 |
| 범위 확장 | 대표 사건 밖 기능이 추가됨 | P0·제외 범위와 결정 로그 |
| 데이터 부정확 | 접근·시점·schema·권리 확인 실패 | 검증된 소규모 데이터와 명시된 mock |
| LLM 출력 불안정 | 형식 오류·환각 반복 | 구조화 출력, 다단계 gate, 규칙 기반 fallback |
| 에이전트 비용·루프 | 재시도와 호출이 계속 증가 | 작업 봉투의 예산·중단 조건 |
| 데모 장애 | 네트워크·API 지연 | 캐시, 사전 데이터, 오프라인 축소 모드, 녹화본 |
| 발표와 제품 불일치 | 슬라이드 기능이 실제 동작하지 않음 | 기능 동결 후 실제 화면만 사용 |

## 선택 전 금지

- 후보별 P0 구현 착수
- 메인 브랜드·캐릭터 수 확정
- 특정 LLM·API를 제품 차별점으로 확정
- 고객 근거 없는 기대효과 수치
- AI가 main 병합·배포·외부 제출

기술 위험만 확인하는 spike가 필요하면 대상 가설·시간 상한·폐기 조건을 실험 카드로 먼저 기록합니다.

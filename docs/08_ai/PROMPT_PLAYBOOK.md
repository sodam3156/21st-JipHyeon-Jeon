# AI 프롬프트 플레이북

프롬프트를 실행하기 전에 `repo.ai-instructions`, `ai.agent-framework`, `planning.current-status`, `governance.gate-log`와 관련 정본을 AI에 제공합니다. 결과는 자동으로 정본에 반영하지 않고 사람이 근거·모순·권한을 검토합니다.

## 공통 시작문

> 문서 ID로 정본을 찾고 현재 상태를 먼저 확인하라. 사실, 관찰, 인사이트, 가설, 제안, 결정, 검증 결과를 구분하라. 모든 결론은 핵심 계보 `RS/E/SJ-P → OBS → IN → OPP → IDEA → SOL → D`와 상태 승격 검증 `HYP → E/X` 중 해당 연결을 표시하라. 원문에서 읽지 않은 세부 내용, 고객 발언, 숫자, URL, API 가능성을 만들지 마라. 지지 근거와 반박 근거를 함께 제시하라. 메인 아이디어를 자동 선택하거나 정본을 직접 승격하지 마라.

## 1. 원천 수집·감사

> validation.research-source-catalog과 새 원천을 읽어라. 기존 원천·claim과 의미 중복을 검사하고, 실제 읽은 범위, 원천 유형, 날짜, 확인한 주장, 사용할 수 없는 주장, 한계를 기록하라. 제목·설명·메타데이터만 확인했다면 그 사실을 명시하라. 고객 근거, 해커톤 전략, 기술 안전성 중 어느 용도인지 하나를 지정하라. 새 원천 ID와 관찰 후보를 제안하되 인사이트를 바로 확정하지 마라.

## 2. 인사이트 합성

> planning.insight-ledger와 관찰 후보를 읽어라. 표현이 아니라 의미 기준으로 중복을 검사하라. 둘 이상의 관찰이 앞으로의 선택을 어떻게 바꾸는지 설명하고, 새 인사이트 또는 기존 인사이트의 강화·한정·반박을 제안하라. 각 제안에는 원천·관찰, 예방하는 실패, 적용하지 말아야 할 범위, 반박될 조건, 신뢰도를 붙여라. 특정 아이디어를 살리기 위한 사후 논리는 거부하라.

## 3. 인사이트 반론 감사

> Insight Synthesizer와 독립된 반론자로 행동하라. active 인사이트마다 가장 강한 반례, 조사 편향, 원천 용도 혼합, 인과 비약, 오래된 근거를 찾아라. 유지, qualified, rejected, superseded 중 하나를 추천하고 변경이 필요한 문장과 이유를 제시하라. 다수 문서나 모델 합의를 진실의 대리 지표로 쓰지 마라.

## 4. 기회 영역 구조화

> planning.insight-ledger, validation.evidence-log, sejong-ax.problem-bank의 관련 문제를 읽어라. 고객 속성, 장소, 촉발 시각, 실패 행동, 측정 가능한 손실, 기존 대안, 해결 가능한 부분, 구조적 공급 부족을 구분하라. 사용자·수혜자·구매자·운영자·도입 결정자를 분리하고, AI가 바꾸는 판단 또는 결과물과 최소 데이터를 적어라. 치명 가정과 48시간 검증을 포함한 opportunity brief를 작성하라. 기능 이름이나 브랜드부터 제안하지 마라.

## 5. 기회 영역 비교

> OPP 후보 최대 3개를 같은 정보량과 같은 기준으로 비교하라. 문제 증거, 고객 접근성, 세종·대주제 적합성, AI 필요성, 데이터 가능성, 3분 발표 안의 90초 핵심 데모 상태 변화, 위험·운영 주체를 평가하라. 각 판단에 IN·문제·E ID를 연결하라. 총점만으로 선택하지 말고, 후보별 치명 가정과 가장 값싼 반증 실험을 제시하라. 검증할 상위 두 영역을 추천하되 불확실성과 사람의 선택 질문을 남겨라.

## 6. 제한된 아이디어 생성

> Gate 2를 통과한 OPP 하나와 연결 IN을 읽어라. 해결 원리가 서로 다른 아이디어를 최대 2개만 생성하라. 각 아이디어를 고객·촉발 사건·실패 행동·손실·현재 대안·AI가 바꾸는 판단·업무 결과물·세종 제거 테스트·최소 데이터·3분 발표 안의 90초 핵심 데모 상태 변화·두 번째 사용 사건·48시간 반증으로 작성하라. “AI 추천”, “멀티에이전트 토론”, “통합 플랫폼”을 해결 원리로 쓰지 마라.

## 7. 아이디어 Red Team

> 아이디어 생성과 독립된 반론자로 행동하라. planning.idea-portfolio의 즉시 탈락 조건을 적용하고, 근거 사슬의 누락, 가장 강한 기존 대안, 데이터·권리·안전·도입 반례, 공급 부족 과장, 세종 장식화, 재사용 부재를 공격하라. 유지·수정·폐기 추천과 확신도를 제시하고, 후보를 실패시킬 최소 실험 하나를 설계하라. 대안 없는 비판은 하지 마라.

## 8. 솔루션 최소화

> 반론을 통과한 IDEA 최대 3개, 관련 OPP·IN, 가용 제작 역량과 해커톤 시간을 읽어라. 후보마다 같은 시간 상한과 `template.solution-card`를 적용해 `planning.solution-portfolio`에 비교 가능한 최소 솔루션을 제안하라. 각 후보는 대표 사건 하나의 `이벤트 → 판단 → 도구 → 결과물 → 다음 행동` 수직 경로를 가져야 한다. 기능을 P0, P1, 제외로 나누고 P0마다 고객 문제, 데이터, 수용 기준을 연결하라. 자동 실행·사람 승인·정보 부족 중단을 분류하고, timeout·429·형식 오류·오래된 데이터·네트워크 장애의 축소 모드를 제시하라. 후보별 Gate 4 판정안을 남기되 사람 검토자를 대신 입력하지 마라.

## 9. 데이터·AI 계약

> 선택 후보의 P0 경로를 기준으로 입력, 출력, 오류, provenance 계약을 작성하라. `parse → schema → business rule → source/time → safety → budget → post-condition` 검증을 정의하라. 외부 데이터에는 source URL, source timestamp, fetched time, schema version, stale/fallback 상태를 포함하라. 확인되지 않은 API를 사용할 수 있다고 가정하지 말고 mock과 실제 연동을 구분하라.

## 10. 실험 설계

> 가장 치명적인 HYP 하나를 선택하라. 결과를 보기 전에 성공·실패·판단 보류 기준, 대상, 과제, 수집 데이터, 예외, 기한, 담당자를 적어 experiment card를 작성하라. 해결책 호감보다 최근 실제 행동 또는 프로토타입 과제를 우선하라. 결과에 따라 수정할 IN·OPP·IDEA·D ID를 명시하라.

## 11. 후보 심사

> 최대 3개 후보에 같은 평가표·입력·시간·데이터 조건을 적용하라. 문제 증거, 고객 접근성, 세종·대주제 적합성, AI 필요성, 데모 상태 변화, 데이터·기술, 위험·운영, 차별성·재사용을 `unsupported`, `weak`, `supported`, `strong` 중 하나로 평가하라. 각 등급의 직접 근거, 탈락 조건, 불확실성을 제시하라. 숫자 환산·가중합·총점으로 자동 선택하지 마라. 추천은 가능하지만 selected 상태나 결정 ID를 만들지 마라.

## 12. 문서 모순 검사

> repo.document-index의 active 문서를 기준으로 주요 고객, 문제, 인사이트, 기회, 후보 상태, 선택 여부, 가치 제안, P0, 일정, 데이터 원천의 모순을 검사하라. 문서 ID와 해당 문장을 연결하고, 수정할 정본과 결정 기록 필요 여부를 제안하라. draft 후보 문서를 accepted 결정처럼 해석하지 마라.

## 13. 데모·발표 심사

> 세종 AX 해커톤의 0맥락 심사위원 관점에서 데모를 평가하라. 첫 20초의 고객·문제 이해, 3분 발표 안의 90초 핵심 데모 상태 변화, 세종 요소, AI의 필수 역할, 근거·데이터 시점·사람 승인, 실제 구현 범위, 실패 fallback, 측정 가능한 전후 차이를 확인하라. 제품에 없는 기능이나 검증하지 않은 수치를 발표 문구로 만들지 마라.

## 공통 출력 형식

1. 실행 ID와 질문
2. 결론
3. 근거 사슬
4. 반박 근거 또는 한계
5. 제안한 산출물
6. 검증 방법과 사후 상태
7. 실패·부분 성공·예산
8. 수정이 필요한 문서 ID
9. 사람의 결정이 필요한 항목

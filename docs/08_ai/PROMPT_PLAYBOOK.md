# AI 프롬프트 플레이북

프롬프트를 실행하기 전에 AGENTS.md와 관련 정본 문서를 AI에 함께 제공합니다. 결과는 자동으로 정본에 반영하지 말고 사람이 근거와 모순을 검토합니다.

## 1. 문제 정의 비판

> AGENTS.md, planning.problem-definition, planning.primary-customer, validation.evidence-log를 읽어라. 현재 문제 정의를 고객 구체성, 상황 구체성, 문제 빈도, 심각도, 기존 대안, 접근성, AI 필요성, 해커톤 구현 가능성 기준으로 비판하라. 사실·근거·가설·미정을 구분하고, 문서에 없는 고객 발언이나 숫자를 만들지 마라. 가장 치명적인 미검증 가설 3개와 각 가설을 48시간 안에 반증할 실험을 제안하라.

## 2. 인터뷰 기록 분석

> 인터뷰 원문을 요약하기 전에 최근 실제 행동, 사용한 도구, 소요 시간, 실패 원인, 감정, 우회 방법을 추출하라. 해결책에 대한 호감 표현보다 실제 행동을 높은 근거로 평가하라. 공통 패턴과 예외를 분리하고, 각 결론에 인터뷰 ID를 붙여라. 현재 문제 가설을 지지하는 근거와 반박하는 근거를 같은 비중으로 제시하라.

## 3. 솔루션 범위 축소

> planning.problem-definition, planning.primary-customer, planning.solution-brief, product.prd, delivery.hackathon-plan을 읽어라. 8월 11일 3분 데모에서 문제 해결이 보이는 최소 사용자 흐름을 제안하라. 각 기능을 P0, P1, 제외로 분류하고 P0마다 고객 문제와 수용 기준을 연결하라. 단순히 멋있어 보이거나 실제 다중 에이전트가 필요하다는 이유로 기능을 남기지 마라.

## 4. PRD 모순 검사

> 문서 색인의 모든 active 문서를 기준으로 product.prd를 검사하라. 주요 고객, 핵심 문제, 가치 제안, P0 범위, 일정, 데이터 원천이 서로 모순되는 지점을 표로 정리하라. 문서 ID와 해당 문장을 인용하되 원문을 과도하게 복사하지 마라. 수정이 필요한 정본과 결정 기록 필요 여부를 제안하라.

## 5. 데모·발표 심사

> 세종 AX 해커톤 심사위원 관점에서 현재 데모 스토리를 평가하라. 문제 실제성, 고객 구체성, 세종 연관성, AI 필요성, 구현 완성도, 차별성, 시연 안정성별로 5점 척도와 근거를 제시하라. 점수를 높이기 위한 행동은 남은 기간에 실행 가능한 것만 제안하라. 제품에 없는 기능을 발표 문구로 만들지 마라.

## 공통 출력 형식

1. 결론
2. 확인된 근거
3. 반박 근거 또는 한계
4. 가장 위험한 가설
5. 권장 행동과 완료 조건
6. 수정이 필요한 문서 ID
7. 사람의 결정이 필요한 항목

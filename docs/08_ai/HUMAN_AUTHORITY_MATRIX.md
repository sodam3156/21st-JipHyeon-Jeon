# 인간 책임·승인 권한 행렬

## 목적

AI와 다섯 명의 팀원이 각 작업에서 누가 실행하고, 누가 검토하며, 누가 최종 승인하는지 일관되게 판단하도록 합니다.

승인은 위험 통제만을 위한 절차가 아닙니다. 고객 맥락, 팀의 실제 역량, 사용성, 미감, 관계 형성처럼 인간이 더 좋은 결과를 내는 영역은 인간이 직접 실행하거나 승인합니다.

## 인간 역할 이름

| 역할 이름 | 담당자 | 책임 영역 | AI가 대체할 수 없는 책임 |
|---|---|---|---|
| 팀장PM | 백서준 | 팀장, PM, 협업 조율, 백엔드 서브 | 우선순위, 메인 아이디어, P0, 일정·발표·대외 범위 최종 결정 |
| 기획QA | 손시우 | QA, 콘텐츠 기획, 페르소나·프롬프트, 협업 조율 | 실제 사용성 판정, 고객·문제 맥락, 버그 심각도와 콘텐츠 적합성 |
| 백엔드보안 | 최영 | 메인 백엔드·AI, API·DB, 개인정보 최소수집, 세션·보안 | 보안·개인정보·세션 위험 승인, 백엔드·AI 실행 가능성 판정 |
| 프론트UX | 여하윤 | UI/UX, 프론트엔드, 토론 뷰·체크리스트·리더보드 | 상호작용 구조, 웹 구현 가능성, 통합 사용자 흐름 승인 |
| 비주얼디자인 | 김경은 | 캐릭터·비주얼, 웹 레이아웃·오브제 배치 | 캐릭터 정체성, 시각 위계, 집현전 세계관과 표현 품질 승인 |

## 권한 등급

| 등급 | 실행 규칙 | 예시 |
|---|---|---|
| A — AI 자율 | 가역적 작업을 수행하고 결과·검증을 기록 | 자료 정리, 중복 검사, 초안, 로컬 테스트 |
| B — AI 실행·인간 검토 | AI가 완성안을 만들고 분야 책임자가 검토 | 문서·코드 패치, 프롬프트 초안, UI 초안 |
| C — 인간 실행·AI 보조 | AI는 준비·기록·분석만 하고 사람을 대신해 완료 처리하지 않음 | 고객 인터뷰, 현장 관찰, 팀 협의, 사용성 테스트 |
| D — 인간 결정 | AI는 승인 패킷과 추천만 제출 | 고객·문제·P0·메인 아이디어·예산 결정 |
| E — 이중 승인 | 분야 책임자와 팀장PM이 모두 승인 | main 병합, 배포, 외부 제출, 민감정보·비가역 변경 |

응답이 없으면 승인으로 간주하지 않습니다. 승인 전 상태는 `blocked` 또는 `review`로 유지합니다.

| 고객·문제 정의·콘텐츠 | 기획QA | 기획QA | P0·전략 변경 시 팀장PM | C/D |
| 고객 인터뷰·현장 검증 | 기획QA 또는 지정 팀원 | 기획QA | 결과 해석이 선택을 바꾸면 팀장PM | C |
| 페르소나·프롬프트 | 기획QA | 기획QA | 구조화 출력·API 영향은 백엔드보안 | B |

| 캐릭터·비주얼·오브제 | 비주얼디자인 | 비주얼디자인 | 웹 적용은 프론트UX | B |

## 상호 검토 규칙

- 자신의 구현을 혼자 최종 승인하지 않습니다.
- 최영이 백엔드를 구현하면 백서준이 기능 검토하고, 백서준이 구현하면 최영이 검토합니다.
- UI/UX 변경은 여하윤이 구현 책임을 지고 손시우가 사용성을, 김경은이 시각 품질을 검토합니다.
- 캐릭터·비주얼 변경은 김경은이 승인하고 여하윤이 웹 적용 가능성을 확인합니다.
- 고객·문제 판단은 손시우가 근거 품질을 승인하고, 범위나 일정이 바뀌면 백서준이 최종 결정합니다.
- 모델 간 합의와 AI 다수결은 인간 승인을 대신하지 않습니다.

## 차단권과 waiver

다음 분야 책임자는 근거를 남겨 작업을 차단할 수 있습니다.

- 기획QA: 고객 근거 부족, 사용성 실패, 버그 심각도 미해결
- 백엔드보안: 개인정보·세션·보안 취약점, 핵심 API·DB 계약 실패
- 프론트UX: 핵심 사용자 흐름 미완성, 브라우저에서 재현 불가
- 비주얼디자인: 캐릭터 정체성 훼손, 정보 위계·가독성 실패
- 팀장PM: 일정·P0·해커톤 제약 위반

일반 차단은 팀장PM이 이유·완화책·만료일이 있는 waiver를 제안할 수 있습니다. 다만 실제 개인정보·비밀값 노출, 미승인 외부 발송, 재현 가능한 중대 보안 취약점은 waiver할 수 없습니다. 해커톤 시연에서는 해당 기능을 제거하거나 합성 데이터·오프라인 축소 모드로 전환합니다.

## 부재와 대체 승인

- 승인자를 임의로 추정하거나 자동 대체하지 않습니다.
- 대체 승인자는 승인 패킷에 담당자·기간·범위를 명시한 경우에만 유효합니다.
- 백엔드보안 부재 중 보안·개인정보 판단이 필요하면 실제 데이터 사용을 중단하고 합성 데이터 경로만 허용합니다.
- 기획QA 부재 중 고객 검증은 인터뷰 준비까지만 진행하고 결과 승격은 보류합니다.
- 프론트UX 또는 비주얼디자인 부재 중 해당 분야 산출물은 draft 상태를 유지합니다.
- 팀장PM 부재 중 D·E 등급 결정은 자동 통과하지 않습니다.

## 승인 패킷

B–E 등급 작업은 필요 시 `template.approval-packet`을 사용합니다. 최소한 다음을 포함합니다.

- 승인 ID와 연결 AR·D·X ID
- 결정 질문 하나
- 권한 등급과 담당 승인자
- 선택지·추천·지지 근거·반박 근거
- 승인·수정·거절 시 영향
- 승인 범위·만료 조건
- 응답 없을 때의 차단 상태
- 실제 승인자·승인일·결과

## 에이전트 역할과 인간 연결

| AI 역할 | 기본 인간 책임자 |
|---|---|
| Source Curator, Insight Synthesizer, Opportunity Mapper, Experiment Designer | 기획QA |
| Ideator, Judge, Orchestrator | 팀장PM; 고객 판단은 기획QA 공동 검토 |
| Red Team | 생성 담당자와 다른 인간 책임자; 분야에 따라 기획QA·백엔드보안·프론트UX |
| Solution Architect | 백엔드보안·프론트UX; P0와 데모 범위는 팀장PM |
| 보안·개인정보 평가 | 백엔드보안 |
| UI/UX 검증 | 프론트UX·기획QA |
| 캐릭터·비주얼 검증 | 비주얼디자인 |

## 승인 기록 원칙

- 승인 요청과 결과는 `governance.approval-log`에 사람 이름, 날짜, 범위, 결과로 남깁니다.
- `approve`, `revise`, `reject`, `defer` 중 하나를 사용합니다.
- 승인 후 입력·P0·데이터·권한 범위가 바뀌면 다시 승인받습니다.
- 의견 불일치는 삭제하지 않고 반대 근거와 최종 결정 이유를 기록합니다.
